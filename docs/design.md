# 设计说明

面向想改这个工具、或想搞清楚"它到底做了什么"的人。
用法在 [`README.md`](../README.md)，这里只讲**怎么做的**和**为什么这么做**。

---

## 整体流程

```
        ┌──────────────┐
        │ 1. 扫描      │  walkdir 递归，只收普通文件
        └──────┬───────┘  reparse point 记下来，不跟进
               │
        ┌──────▼───────┐
        │ 2. 筛候选    │  只有"尺寸重复"的文件才可能内容重复
        └──────┬───────┘  ← 这一步把读盘量压到最小
               │
        ┌──────▼───────┐
        │ 3. 算摘要    │  rayon 并行 SHA-256，只读候选
        └──────┬───────┘
               │
        ┌──────▼───────┐
        │ 4. 聚合      │  按 (尺寸, 摘要) 分桶 → 重复组
        └──────┬───────┘  再与主副本比文件身份 → 待转换 / 已链接
               │
        ┌──────▼───────┐
        │ 5. 报告+确认 │  列出清单，用户选范围
        └──────┬───────┘
               │
        ┌──────▼───────┐
        │ 6. 转换      │  改名 → 建链 → 校验 → 删除
        └──────┬───────┘
               │
        ┌──────▼───────┐
        │ 7. 复核      │  重新 stat，确认与主副本共享身份
        └──────────────┘
```

---

## 为什么分"按尺寸"和"按摘要"两步

判定重复的**唯一可靠依据是内容**。但对整个目录树的所有文件都算摘要，读盘量是灾难性的
（一棵 55 GB 的树有上万个文件）。

分两步的好处是**第二步的读盘量只与"尺寸重复"的文件数成正比**，而不是与文件总数成正比。
实测：一棵 55.63 GB / 11049 文件的树，只有 6036 个候选需要读盘。

对 6036 个候选算 SHA-256 的耗时在 1 秒量级（并行）。

---

## 文件身份：为什么必须看 inode

只比较内容，无法区分这两种情况：

```
a.txt  与  b.txt   内容相同，但是两份独立数据
a.txt  与  b.txt   内容相同，且已经是同一份硬链接
```

第一种该合并，第二种不该再动。工具用**操作系统级的文件身份**做这个区分：

| 平台 | 身份 |
|------|------|
| Windows | 卷序列号 + 文件索引号（`GetFileInformationByHandle`）|
| Unix | device + inode |

实现走 `same-file` crate。它是稳定 API；`std::os::windows::fs::MetadataExt` 的
`file_index()` / `number_of_links()` 至今仍是 unstable，不能作为依赖。

**这个身份判定是幂等性的基础** —— 没有它，第二次运行会把已链接的文件再"合并"一遍。

### 一个必须小心的地方

`is_same_file` 返回 `Option<bool>`：`None` 表示**无法判断**（例如文件被独占锁定）。
调用方不能把 `None` 当成 `false` —— 那会导致把已链接的文件当成独立副本再处理一遍。
本项目统一按"无法判断 = 尚未链接"处理，宁可多处理一次也不误判。

## 主副本的选择

每一组里保留哪一个路径继续持有数据。规则集中在一个函数里，按顺序比较：

1. **不在临时/工作目录里的优先** —— 主副本要放在用户真正会打开的目录里。
   agent 工作区（`.agents`）、缓存（`cache`）、临时目录（`temp`/`tmp`）随时可能被清理，
   主副本放在那里等于把数据的存活挂在临时目录上
2. **没有 `(1)` 这类副本标记的优先** —— 它是用户看到的"原名"
3. **修改时间更早的优先** —— 保留"最初那份"的语义
4. **路径更短的优先**
5. **路径字典序** —— 保证同一批文件每次都得到相同结果

第 5 条是刻意加的：前四条可能出现平局，没有它就可能出现"同一批文件两次运行选到不同主副本"
的抖动。

**副本内容完全相同**，所以把数据留在哪个路径不损失任何东西 —— 这条规则只是让结果更符合直觉。

## 安全执行序列

每个副本的处理是一个多步序列。**顺序本身就是安全承诺**：

```
1. rename(副本) → 副本.duplink.tmp      原始数据仍在盘上，任何失败都可原样恢复
2. hard_link(主副本, 副本)              两个路径共享同一份数据
3. 校验：新链接与主副本确实是同一文件   不一致立即撤销
4. 清除只读位 → 删除临时文件            到这一步磁盘占用才真正下降
```

### 为什么不是"先建链接、再删原件"

那样一旦建链失败（跨卷、权限、文件被锁），原始数据已经被删掉了，无法回退。

当前顺序把"**数据仍独占存在**"的状态延长到建链与校验全部完成之后。
第 4 步之前，任何失败都能做到：移除半成品链接 → 把临时文件改回原名 →
**原文件内容字节级不变**。

### 第 4 步为什么要清只读位

Windows 上删除只读文件会失败。微信等程序会给接收到的文件加只读位，
不先清掉就删不掉。Unix 上删除取决于**目录**权限而非文件自身的只读位，
所以那里不做任何权限改动（避免把文件变成 world-writable）。

### 跨卷会怎样

硬链接不能跨卷。若主副本与副本不在同一个卷，`hard_link` 会失败 ——
按上面的回退路径，原文件被完整恢复，工具报告错误并继续处理其它组。
这是"主副本与副本必须在同一个盘符"这条限制的来源。

## reparse point（符号链接 / 目录联接）策略

扫描**不会跟进**它们。这是刻意设计，不是遗漏：

- 联接可能指向扫描根**之外**，把根外的文件算进来会让"可回收空间"失真
- 联接可能指向自身的**祖先**，跟进去会成环
- 联接可能指向树内**已经扫过**的目录，跟进去会把同一批文件重复计数

但这些条目**遮蔽**的文件必须让用户知道 —— 否则"扫描了 11049 个文件"会让人以为
整棵树都覆盖到了。报告会逐个列出位置、目标与遮蔽的文件数。

统计遮蔽量必须**有界**，否则一个指向自身祖先的联接会让程序挂死。三重保险：

1. 限制遍历深度
2. 用**规范化路径**去重（`canonicalize` 把联接展开成真实目标，指向祖先的链接因此命中同一 key）
3. 限制文件总量

每个 reparse point **独立**统计：共享去重集合会让"两个目标指向同一批文件"的情况漏计
（实测漏掉了 1808 个）。独立统计给出的是各目标子树各自的真实体量，
汇总值可能因目标重叠而偏大 —— 报告里会注明这一点。

## 幂等性

第二次运行的结果应该是"0 份待转换"。做到这一点靠两件事：

1. **文件身份判定** —— 已共享数据的成员被识别出来，标为"已链接"而不再处理
2. **可复现的主副本选择** —— 规则第 5 条（字典序）保证主副本不会在两次运行间漂移

副作用是：即使某个文件的身份取不到（被锁定），它会被当成"尚未链接"重新处理一次 ——
此时建链会成功（内容相同），或失败并回滚。两种情况都不会损坏数据。

## 性能特征

| 阶段 | 复杂度 |
|------|--------|
| 扫描 | O(文件数)，只读元数据 |
| 筛候选 | O(文件数) |
| 算摘要 | O(候选数 × 文件大小)，**并行** |
| 聚合 | O(文件数) |
| 转换 | O(待转换数)，每次涉及一次改名 + 一次建链 + 校验 |

实测参考：55.63 GB / 11049 文件的目录树，扫描 + 摘要约 1~3 秒（取决于磁盘与线程数）。

## 验证方法：盲审

这个工具的多个 bug 是在**用另一套独立实现复算同一份数据**时抓出来的。
这个方法值得保留，贡献新功能时也建议照做：

1. 用**不同的语言与不同的哈希算法**另写一份实现
   （本项目用过 Python + MD5 + `os.scandir` + `os.path.samefile` 去核对 Rust + SHA-256 + walkdir）
2. 逐项对账：文件数、候选数、重复组数、冗余副本数、**可回收字节（精确到字节）**、
   组成员集合、主副本选择
3. 抽样做**字节级**直读比对，不经任何摘要
4. 差异出现时，**先怀疑自己的审计脚本**：常见陷阱是
   `DirEntry.stat(follow_symlinks=False)` 在 Windows 上 `st_ino` 恒为 0，
   以及 Python 对 junction 的 `islink()` 返回 `False`

本项目曾因这套方法发现三类真实缺陷：报告把"成员总数"写成"待转换数"、
跳过的符号链接遮蔽量未报告、主副本可能落在临时工作目录。

## 退出行为

面向用户的命令行程序不能"闪退"。双击 exe 运行时 Windows 会新建控制台窗口，
进程一结束窗口就关闭 —— 程序其实正常跑完了，但用户什么都看不到。

处理规则：

| 场景 | 行为 |
|------|------|
| 双击启动（无参数） | 结束前停在「按回车键关闭窗口…」 |
| 报错退出 | 停在「按回车键关闭（出错信息如上，请先读完再关）」 |
| `--help` / `--version` | 停在「按回车键关闭窗口…」 |
| panic | 打印可读诊断（原因、代码位置、数据安全说明），然后停在窗口里 |
| 带参数运行 | 正常结束即退出 |
| 管道 / 重定向 / 脚本 | 正常结束即退出，**绝不阻塞** |

判定依据是 stdout 与 stdin **同时**是终端才算"有人在看"。只要有一端被重定向，
本次运行就可能处在自动化流程里，等待回车会卡死脚本。

panic 钩子把 Rust 默认的一行英文信息换成可读诊断，让用户能截图反馈而不是只看到"闪退"。
