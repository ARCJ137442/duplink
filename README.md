# duplink · 重复文件检测与硬链接合并

> Duplicate Finder & Hardlink Merger

一个用 Rust 写的命令行工具：递归扫描目录、找出**内容完全相同**的重复文件，在用户确认后
把它们转换为**硬链接**，从而让多份副本只占一份磁盘空间。

---

## 功能特性

### 主要功能

- **自动扫描**：默认从**程序所在目录**开始递归遍历；也可用 `--path` 指定任意目录
- **内容级判定**：先用文件大小缩小候选，再算 SHA-256 摘要确认内容一致——不是比文件名
- **识别已链接**：能分辨"内容相同但独立的两个文件"与"已经是硬链接的同一份数据"
- **交互确认**：列出全部重复组后，由用户选择处理范围，确认后才动手
- **安全执行**：先改名保留原件 → 建立硬链接 → 校验 → 才删除，失败自动回滚
- **结果复核**：转换完成后重新校验每个路径，确认它与主副本共享同一份磁盘数据
- **重复可运行**：已经是硬链接的副本会被识别并跳过，不会重复处理

### 技术特点

- 按体积分组 + SHA-256 摘要，只对候选文件读盘，大目录树也能快速扫完
- 摘要计算并行执行（rayon），6.5 GB 的目录树约 1 秒完成
- 平台差异集中在 `platform.rs`，其余模块只依赖跨平台语义
- 彩色输出带 emoji，交互提示用中文

## 安装与构建

```bash
cd duplink
cargo build --release
```

产物：`target/release/duplink.exe`（Windows）/ `target/release/duplink`（Linux/macOS）

exe 是单文件、无外部依赖，双击或直接运行即可。

### 部署方式

因为默认扫描"程序所在目录"，有两种用法：

```bash
# 方式一：把 exe 复制到目标目录再运行（默认扫描 exe 所在目录）
copy duplink.exe D:\some\folder\
cd D:\some\folder && duplink.exe

# 方式二：exe 放在固定位置，用 --path 指定扫描目标（推荐）
duplink.exe --path D:\some\folder
```

## 使用方法

### 基本流程

```
duplink.exe --path <目录>
```

1. 扫描目录，统计文件数与总体积
2. 筛出"尺寸与其它文件相同"的候选
3. 并行计算候选文件的 SHA-256
4. 聚合重复组，列出清单与可回收空间
5. 提示选择要处理的组
6. 转换为硬链接
7. 复核并输出结果

### 选择语法

| 输入 | 含义 |
|------|------|
| `all` / `a` / `全部` | 处理全部重复组 |
| `none` / `n` / `无` | 全部跳过 |
| `safe` | 只处理**不含**文本/代码类文件的组 |
| `size>10MB` | 只处理单份大小超过阈值的组 |
| `1-5,8,12-` | 按下标选择（从 1 开始，`12-` 表示到末尾） |

以上可用逗号组合，例如 `1-5,safe`。

## 命令行参数

| 参数 | 说明 |
|------|------|
| `-p, --path <DIR>` | 扫描根目录（默认：程序所在目录） |
| `-s, --min-size <SIZE>` | 只处理不小于该大小的文件，如 `1MB` / `500KB` / `2GB` |
| `-e, --exclude <GLOB>` | 排除匹配的路径，可重复使用 |
| `--max-depth <N>` | 扫描最大深度（0 = 只看根目录） |
| `--jobs <N>` | 并行计算摘要的线程数（默认 = CPU 核数） |
| `-d, --dry-run` | 预览模式：只报告，不做任何改动 |
| `-y, --yes` | 跳过交互确认，直接处理全部 |
| `--json` | 以 JSON 输出结果（JSON 到 stdout，人类信息到 stderr） |
| `--max-listed <N>` | 报告中最多列出几组（0 = 不限制，默认 200） |

### 排除规则

模式同时匹配"相对扫描根目录的完整路径"和"路径中的任意一段"：

| 模式 | 效果 |
|------|------|
| `target` | 排除任意层级的 target 目录 |
| `*.tmp` | 排除任意层级的 .tmp 文件 |
| `sub/*.tmp` | 只排除 sub 目录第一层的 .tmp 文件 |

## 工作原理

### 主副本的选择

每一组里保留哪一个路径继续持有数据，是这个工具最需要解释的决定。规则按顺序比较：

1. **没有 `(1)` 这类副本标记的优先** —— 它是用户看到的"原名"
2. **修改时间更早的优先** —— 保留"最初那份"的语义
3. **路径更短的优先**
4. **路径字典序** —— 保证每次运行得到相同结果

其余副本被转换为指向主副本的硬链接。

### 安全执行序列

每个副本的处理是一个多步序列，**顺序本身是安全承诺**：

```
1. rename(副本) → 副本.duplink.tmp      原始数据仍在盘上，任何失败都可原样恢复
2. hard_link(主副本, 副本)              两个路径共享同一份数据
3. 校验：新链接与主副本确实是同一文件   不一致立即撤销
4. 清除只读位 → 删除临时文件            到这一步磁盘占用才真正下降
```

为什么不是"先建链接、再删原件"？那样一旦建链失败，原始数据已经被删掉，无法回退。
当前顺序把"数据仍独占存在"的状态延长到建链与校验全部完成之后。

任何一步失败都会：移除半成品链接 → 把临时文件改回原名 → 报告错误。
**失败时原文件内容字节级不变。**

### 为什么判定"是否同一文件"必须看文件身份

只比较文件内容，无法区分：

- `a.txt` 和 `b.txt` —— 内容相同，但是两份独立数据
- `a.txt` 和 `b.txt` —— 内容相同，且已经是同一份硬链接

工具用操作系统级的文件身份（Windows 上是卷序列号 + 文件索引号，Unix 上是 device + inode）
来做这个区分。这也是"重复运行不重复处理"的基础。

## 已知限制

### ⚠️ 文本与代码文件：原地编辑会互相影响

硬链接之后，多个路径共享同一份数据。用编辑器**原地保存**其中一个（例如
"保存"而不是"另存为"），其余路径的内容会同步改变。

报告阶段会标出受影响的组，可以用 `safe` 选项整体排除。

二进制文件（图片、音频、视频、压缩包、PDF 等）不存在这个问题。

### 其它限制

- **硬链接不能跨卷**：主副本与副本必须在同一个卷上（同一个盘符）
- **时间戳会统一**：转换后所有路径共享主副本的修改时间，无法保留各自的 mtime
- **符号链接不参与去重**：避免跨目录成环与链接到目录外的同一份数据导致分组失真
- **空文件跳过**：不占实际空间，没有去重价值
- **只读属性会自动清除**：Windows 上删除只读文件必须先清只读位（微信等程序会给收到的文件加只读）

## 项目结构

```
duplink/
├── src/
│   ├── main.rs      # 薄编排：扫描 → 摘要 → 分组 → 报告 → 确认 → 转换 → 复核
│   ├── cli.rs       # 命令行参数契约
│   ├── model.rs     # 领域类型：FileEntry / DuplicateGroup / Digest
│   ├── platform.rs  # 平台差异隔离：文件身份比较、只读位处理
│   ├── scan.rs      # 目录遍历与候选筛选
│   ├── digest.rs    # 并行 SHA-256
│   ├── group.rs     # 分组与主副本选择策略
│   ├── link.rs      # 硬链接执行（唯一有破坏性副作用的模块）
│   ├── report.rs    # 报告渲染（人类可读 + JSON）
│   └── confirm.rs   # 交互式选择
├── Cargo.toml
├── Cargo.lock
└── README.md
```
